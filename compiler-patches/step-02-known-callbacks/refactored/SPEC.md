# 既知のcallbackの特殊化

この変更は、BendのC生成バックエンドで、呼び出し先に渡すlambdaが静的に分かる場合にclosureの確保と動的適用を省く最適化を追加する。GPUIのパーティクル更新は、その効果と正しさを確認する実例として扱う。

## What

ユーザーは通常の関数とcallbackを書ける。

```python
def apply(x: U32, callback: U32 -> U32) -> U32:
  callback(x)

def run(+bias: U32, x: U32) -> U32:
  a = apply(x, y => U32.add(y, bias))
  apply(a, y => U32.add(y, bias))
```

現状は、callbackがliteral lambdaであっても、関数引数として渡すためのclosureと動的適用が生成されることがある。対応する呼び出しでは、コンパイラがlambdaを呼び出し先の本体に代入し、既存の引数束縛・関数展開・lambda適用の処理でコードを生成する。ソースのAPI、型、言語構文は変えない。

## Why

callbackによる要素処理や継続の連結を、利用側で引数展開した関数へ書き換えずに実行できるようにする。小さな処理を繰り返す場合、closureの確保、captureの保存、動的適用のコストが計算そのものを上回ることがある。

CPUとGPUは同じC生成処理を使うため、これは両方に適用できる最適化である。Metalの実行確認は行うが、CUDAの実機性能はこの実験の対象に含めない。

## 今回の対応範囲

- 通常の定義に対する完全適用で、literal lambdaの引数が1個ある呼び出し。
- lambdaがcaptureする実行時値のnative layoutに`box`が含まれない場合。配列・関数・boxedなデータのcaptureは従来の処理を使う。
- callee本体に直接の自己参照、bang呼び出し、複数値を並列束縛する`Let`がない場合。
- 値を返して呼び出し元へ戻る途中の展開では、calleeの通常の参照先はflatであり、callback内にも非flatな呼び出しや並列束縛がない場合。
- 型付きのlambdaと、callback引数より前にあるconstructorのパターン束縛を保持する。callbackのbinderは内部的に未使用とし、公開されている関数の型を変更しない。

動的な関数、複数のlambda引数、foreign/bang呼び出し、対象外のcapture・本体、および最適化予算を使い切った呼び出しは、従来のclosureによる処理を使う。この試作はユーザーに明示的な最適化指定を要求しない。

## 正しさの要件

1. interpreter、生成JS、Cの1/4スレッドで同じ結果を返す。最適化はC生成側で行う。
2. 呼び出し元が後で使うcaptureを、展開したcalleeの終了時に解放しない。
3. 非自明な実引数を既存の`Let`処理で束縛し、callbackの代入で評価を複製しない。線形な配列の所有権と解放を保つ。
4. 最適化予算が尽きてもコンパイルと実行が成功する。ANFが呼び出しを作り直しても、同一callee・callbackの採否を維持する。
5. 検査済みの入力bookを変更せず、同一プロセス内のC/JS再コンパイルで状態を持ち越さない。
6. callbackを使わないflatパーティクル実装は、同一の上流コミットと同じ生成Cになる。

## GPUIによる実例

GPUI側の描画、共有バッファ、読み戻し方針を変更せず、Bendのコンパイラだけを比較する。実例では配列要素を読み出す小さな継続を6段連結するため、既知のcallbackを繰り返し特殊化できる。更新処理のclosure segmentが14個から0個になること、独立したfloat32のoracleと画像の検証が通ること、CPU/Metalで更新時間が改善することを確認する。

GPUIのAPI名、粒子の型、Metal用の手書きkernel、描画方式に応じた分岐はコンパイラに追加しない。この結果から、任意のBendプログラム、表示遅延、GPU間の性能優位については結論を出さない。

## PRの単位と提出条件

現在の上流PR候補に含めるのは`bend2/comp.ts`の最適化と、scalar capture、tupleのmatch、線形配列を示すBendの回帰例2ファイルである。予算切れなどの追加検証と、GPUIのバインディング・アプリ・測定ツールはこの実験リポジトリに置き、PR本文から実例として参照する。既存のFFI修正PRとは独立した変更にする。

基準は2026-10-03に確認した上流mainの`947db722640c86247849343657bf2f7ef01cb7f1`。forkの実装は[`b59588e2`](https://github.com/mizchi/bend/commit/b59588e2a9c63092b542739bb6908c3329d2e353)に固定し、[reference.json](reference.json)に両者のコミットとcompiler hashを記録する。現時点の縮小版はコンパイラ69行追加・15行削除で、`comp.ts`が64,777 ttokとなり、64,000の恒久上限を超えている。機能検証とは別に、これを上限内に収めることが提出条件となる。上限の変更や別ファイルへのコード移動で回避しない。

lambda適用だけの切り出しも調べたが、試した通常のソース例は既存の処理で既に簡約されたため、それだけを効果のあるPRとして扱わない。次の整理は、既存のfold・引数束縛・関数展開と重複する処理を統合し、今回の回帰例を保ったままコード量を減らす方向で行う。
