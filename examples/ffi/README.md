# ネイティブ C FFI の呼出しコスト

Bend 2.0.34 の同期 C FFI を、Apple M5 で測る。U32 の状態と処理回数を渡して U32 を受け取る。
呼出し間には依存関係を置き、前の戻り値を次の入力にする。各呼出しで印字や OS の IO は行わない。
この測定の追加時間には、Bend のループ、IO 要求・継続の生成、ホストのディスパッチ、
C 関数の呼出し、戻り値の受取りまでが含まれる。

比較する4種類:

| 実装 | 処理 |
|---|---|
| C direct | 別の翻訳単位の C 関数をループから直接呼ぶ |
| Bend pure | 同じ計算を Bend の純粋なループで実行する |
| Bend IO.pure | FFI 版と同じ IO.bind / 継続の構造で、外部要求を出さずに計算する |
| Bend FFI | IO 要求を出し、登録した C ラッパー経由で C direct と同じ関数を呼ぶ |

C の本体は [kernel.c](kernel.c)。xorshift32 を指定回数実行する。
0回では入力をそのまま返す。C direct と FFI は、どちらも同じ kernel.c を別コンパイルする。
`noinline` を指定し、LTO は使わないため、呼出し側は本体をインライン化したり呼出しを省略したりできない。
Bend は `-o <file>.c` で C に変換し、同じ clang / `-std=c11 -O3 -pthread` でリンクする。

FFI 宣言は [foreign.bend](foreign.bend)、C 側の登録は [effect.c](effect.c)。
引数は U32 2個、返り値は U32 1個。同期ホスト効果を `need=0` で登録する。
GPU・helper thread・文字列・配列・構造体の受渡しは対象に含めない。
1スレッドと全10スレッドのランタイム設定を測るが、このループ自体は逐次実行する。
スレッド数の指定を増やしても、独立した呼出しが並列に走る実験にはならない。

```sh
just check-ffi
just bench-ffi --batch --output build/ffi/results.json

# 呼出し回数と C 内部の仕事量を指定する
just bench-ffi --calls 0 1048576 4194304 16777216 --rounds 0 1
```

各条件は出力を1回照合してから3回直列に測る。プロセス起動と最後の1回の出力は時間に含み、
コンパイルは含めない。中央値を使い、0回の条件以外の3サイズから
`T(N) = a + b × N` を最小二乗で求める。`a` は固定時間、`b` は1呼出し当たりの増分。
最小時間・中央値・3回の個別時間・最大RSSも生ログに残す。

```text
追加コスト（C direct 基準） = b(Bend FFI) - b(C direct)
追加コスト（Bend pure 基準） = b(Bend FFI) - b(Bend pure)
追加コスト（IO.pure 基準）   = b(Bend FFI) - b(Bend IO.pure)
```

これはループ全体の増分から求める平均コストで、個別呼出しをタイマーで挟んだ測定ではない。
IO.pure と純粋ループはコンパイラによる最適化の仕方も変わるため、その差を個々の内部処理の
費用に分解したものとしては扱わない。
0仕事の純粋ループでは計算が省略され得るので、実際に状態を変える1ラウンドの結果も並べる。

まとめて呼ぶ条件では、C 本体の総ラウンド数を `2^26` に固定する。
1呼出しの処理量を16 / 256 / 4096ラウンドに増やし、その分だけ呼出し回数を減らす。
同じ総仕事量と最終 checksum のもとで、FFI の追加時間が薄まるかを比較する。

正しさは、0回・0仕事・1回・複数回の境界条件を Python の xorshift32 と照合する。
4種類の実装と1・4スレッドで一致すること、回帰の単位と固定時間の除去、
不正な入力・出力の拒否を `tests/ffi.py` の5テストで検証する。
`just test` の全33テストが通った。

計測条件は Apple M5、32 GiB、macOS 26.6.2、Apple clang 21、
Bend 2.0.34 (`7d24b8d0235cb9781140512c0f163c48ea84a719`)。
UI アプリは実行中で、こちらから他のベンチやビルドを並行起動していない。
使用したソースとハーネスの SHA-256、環境、個別時間、回帰結果を生ログに保存する。

今回の結果は、**小さいスカラーの同期 C FFI で、C 直接呼出しに対して追加約20 ns／回**。
100万回の呼出しでは、追加約20 msになる。

1ラウンドを実行する条件の回帰結果:

| 実装 | 1スレッド指定 | 10スレッド指定 |
|---|---:|---:|
| C direct | 1.27 ns/回 | — |
| Bend pure | 1.28 ns/回 | 1.33 ns/回 |
| Bend IO.pure | 11.56 ns/回 | 11.11 ns/回 |
| Bend FFI | 20.27 ns/回 | 19.17 ns/回 |

C direct 基準の追加時間は、1スレッドで `20.27 - 1.27 = 19.00 ns/回`、
10スレッド指定で `19.17 - 1.27 = 17.90 ns/回`。
IO.pure 基準では8.71 / 8.06 ns/回の増加だった。
FFI の回帰の R² は0.99983 / 0.99999。
返り値を変えない0仕事の FFI でも、C direct 基準の追加時間は18.58 / 17.99 ns/回だった。
0仕事の Bend pure は計算が省略され、呼出し回数に比例する時間がほぼなかった。

実行順を C→FFI、FFI→C、C→FFI と入れ替え、各実行を3回測って追加確認した。
1スレッドで最大呼出し回数の差から計算すると、1ラウンドで18.17 ns/回、0仕事で20.53 ns/回。
この再確認の値にはプロセスの固定時間も残る。
小数点以下まで一定の値ではなく、今回の条件では**約18〜21 ns/回、概算20 ns/回**と読む。
全条件の checksum は7モードで一致した。

処理をまとめた結果は、C→FFI / FFI→C / C→FFI の3組で求めた中央値で比較した。
どの行も C 内部では合計67,108,864ラウンドを実行する。

| 1呼出しのラウンド数 | 呼出し回数 | C direct | Bend FFI（1スレッド） | C との差 |
|---|---:|---:|---:|---:|
| 256 | 262,144 | 0.090231s | 0.093092s | +3.17% |
| 4096 | 16,384 | 0.090393s | 0.090708s | +0.35% |

元の固定順の計測には、256ラウンドで FFI の方が短くなるなど小さい差の揺れがあった。
処理をまとめるほど境界の追加時間が小さくなることは確認できたが、サブパーセントの差は
プロセス起動やマシンの揺れの影響も受ける。文字列や大きいデータの変換を含む FFI に、
このスカラーの結果をそのまま当てはめない。

[生の計測値と回帰結果](results-macos-m5-2026-10-02.json) に、元の11条件と実行順確認を保存した。
実行順の追加確認は、最初の計測と同じバイナリを使う。

```sh
python3 scripts/ffi_confirm.py build/ffi/results.json
```

計測前後と追加確認後に thermal / performance warning は記録されていなかった。
