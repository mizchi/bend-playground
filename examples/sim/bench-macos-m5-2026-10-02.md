# 最新マージの Mac CPU ベンチマーク（2026-10-02）

Apple M5 の 10 スレッドで、最新マージの全7プログラムを C twin と比較した。
Connect Four は Bend 1 スレッドの **5.3 倍**、C 1 スレッドの **4.8 倍**速い。
葉のプレイアウトを逐次にして対局の束で並列化する最新の変更は、この Mac でも有効だった。

[生の計測値・出力・環境](results-macos-m5-2026-10-02.txt) を保存した。
従来の [Linux / Xeon の結果](results.txt) とは別の環境での計測になる。

| 条件 | 値 |
|---|---|
| Playground | `5469ac86e2ab463a4ae96da6ced22e2d18f14358`（PR #2 のマージ） |
| Bend | 2.0.34、`7d24b8d0235cb9781140512c0f163c48ea84a719` |
| CPU | Apple M5、性能コア4 + 効率コア6、10論理スレッド |
| メモリ | 32 GiB |
| OS | macOS 26.6.2（25G83）、Darwin 25.6.0、arm64 |
| C コンパイラ | Apple clang 21.0.0、`-std=c11 -O3 -ffp-contract=off`、`-lm` |
| コンパイラ実行環境 | Bun 1.3.5 |
| 計測 | Python 3.9.6、直列の best-of-3、プロセス起動を含む wall clock |

各ソースの既定サイズを使い、CPU のみ（`--gpu off`）を測った。
全コアの列は Bend の既定値である10スレッド。コンパイル時間と出力照合は計測に含めない。
RSS は3回の子プロセスの最大値を MiB に換算したもの（生ログの表示は `MB`）。
UI アプリは実行中で、こちらから他のベンチやビルドを同時起動していない。
計測前後に `pmset -g therm` の thermal / performance warning は記録されていなかった。

| プログラム | C 1スレッド | Bend 1スレッド | Bend 10スレッド | Bend の並列化による倍率 | C に対する10スレッドの倍率 |
|---|---:|---:|---:|---:|---:|
| galton | 0.262s | 0.256s | 0.043s | 6.0倍 | 6.1倍 |
| anneal | 0.400s | 0.652s | 0.093s | 7.0倍 | 4.3倍 |
| balls | 0.840s | 2.400s | 0.541s | 4.4倍 | 1.6倍 |
| balls_flat | 0.858s | 1.095s | 0.186s | 5.9倍 | 4.6倍 |
| fmc | 0.279s | 0.339s | 0.051s | 6.6倍 | 5.5倍 |
| mcts | 0.937s | 1.605s | 0.228s | 7.0倍 | 4.1倍 |
| c4 | 2.288s | 2.531s | 0.476s | 5.3倍 | 4.8倍 |

`balls_flat` は同じ出力の `balls` に対して、Bend 1スレッドで2.2倍、10スレッドで2.9倍速い。
C の列は同じ `balls.c` をそれぞれ計測したもので、0.840s と 0.858s の差は別アルゴリズムによるものではない。
`mcts` は1スレッドでは C の1.71倍の時間がかかるが、対局・木の並列化で10スレッドでは C の4.1倍速くなった。

全7本を計測と同じサイズで再実行し、C / Bend 1スレッド / Bend 10スレッドの出力一致を確認した。
`anneal.c` の `exact=976` など C 固有の追加行は比較から除いた。
`c4` は `games()=4`、各組16局・9組で、盤面の評価を含む全10行が一致した。

Connect Four の葉の設定だけを変えた比較も行った。
`build/` 内のコピーで `leaf.fork()` を `False{}` から `True{}` に置き換え、同じ予算・同じ種で測った。

| 葉のプレイアウト | Bend 1スレッド | Bend 10スレッド | 10スレッドの最大RSS |
|---|---:|---:|---:|
| 逐次（最新の既定値） | 2.531s | **0.476s** | 8 MiB |
| fork | 2.548s | **5.083s** | 58 MiB |

両設定の出力は C と完全に同じだった。葉を fork すると10スレッドでは1スレッドの約2倍の時間がかかり、
葉を逐次にした最新の実装に対して約10.7倍遅くなった。

逐次ループ内の fork の費用を、[fork_cost.bend](probes/fork_cost.bend) でも測った。
4096回のループの各回で xorshift の仕事を2本呼ぶ `plain` / `fork` と、
同じ8192本の仕事を最初に1本の fork 木で分割する `tree` の比較になる。

| w | plain 1 / 10スレッド | fork 1 / 10スレッド | tree 1 / 10スレッド |
|---|---|---|---|
| 16 | 0.003 / 0.002s | 0.003 / **0.475s** | 0.003 / 0.002s |
| 64 | 0.003 / 0.003s | 0.003 / **0.515s** | 0.004 / 0.002s |
| 256 | 0.007 / 0.005s | 0.006 / **0.488s** | 0.006 / 0.003s |
| 1024 | 0.015 / 0.013s | 0.014 / **0.478s** | 0.015 / 0.004s |
| 16384 | 0.183 / 0.183s | 0.182 / **0.490s** | 0.183 / 0.027s |
| 65536 | 0.723 / 0.722s | 0.713 / 0.676s | 0.747 / **0.101s** |

小さい仕事（w=16）の追加コストは `(0.475 - 0.002) / 4096` から約116 µs/fork。
これはこの M5・10スレッドでの値で、Linux・4スレッドの約200 µsと同じ条件ではない。
w=65536 では逐次ループ内の fork も plain より約1.07倍速くなるが、最初に分割する tree は約7.4倍まで伸びる。
数 ms の行は起動コストと丸めの影響が大きいため、倍率の評価には使わない。
plain と fork の出力は全サイズで一致した。tree は独立な種から計算して足すため、出力値は異なる。

再計測はリポジトリのルートで行う。

```sh
just test
just bench-sim
WS="16 64 256 1024 16384 65536" just bench-fork
```

Mac 対応として、コア数の取得を `nproc` から `getconf _NPROCESSORS_ONLN` に変更し、
RSS の単位（Darwin は bytes、Linux は KiB）を共通の計測ヘルパーで換算した。
fork プローブの `case` は Mac 標準の Bash 3.2 でも解釈できる形に直した。
計測コマンドの失敗時は結果を出さず停止する。`just test` は既存8件と計測用4件の全12件が通った。
